CURATOR 0.3.0 — operational reference
======================================

Curator is a self-hosted gallery-dl frontend. It stores sources, media
metadata, ratings, groups, tags, downloads, and browser UI state locally.
It binds only to loopback and explicitly detected Tailscale addresses; it
never binds an ordinary LAN interface or a wildcard address.


EDITIONS
--------

Curator Server (`curator`)
    Headless Rust backend, browser UI/API, downloads, media serving, console
    mode, and background-service mode. It owns a data directory.

Curator Host (`Curator`)
    Native Slint desktop application with the same backend and local
    integrations. It owns a data directory and calls the Rust core directly.

Curator Viewer (`curator-viewer`)
    Lightweight native Slint client for saved Tailnet hosts. It starts no SQLite
    database, no downloader, and no HTTP server. It validates and pins remote
    requests to a Tailnet peer address.

Host and Server acquire an exclusive OS lock at <data-dir>/.curator-data.lock
before SQLite opens. Do not attempt to make two backend processes share a data
directory; Curator intentionally rejects it.


COMMANDS
--------

    curator
        Start Curator Server in the foreground with the current-user scope.

    curator --background --install-scope current-user
        Explicit background-service invocation used by current-user service
        registration.

    curator --background --install-scope all-users
        Explicit background-service invocation used by machine service
        registration. The surrounding service installer requires elevation.

    curator --data-dir /path/to/data
        Use a one-off explicit data directory. It still receives the exclusive
        ownership lock.

    curator import-host --from /path/to/host-data --install-scope all-users
        Elevated, explicit Host-to-machine-Server migration. The command
        locks source/destination, creates an online SQLite snapshot, copies
        library/archives/thumbnails/backups/managed P-HAR files, and refuses
        an occupied destination. It does not copy Host-local executable paths.

    curator phar-intent --enabled true --install-scope current-user
        Record only P-HAR opt-in intent. It performs no package/model download.
        Installers call this after their file transaction only when the
        unchecked P-HAR option was selected.

    curator --docs
        Print this document.


INSTALLATION SCOPE AND LOCATIONS
--------------------------------

Current user is the default and normally needs no elevation.

Windows current-user Server
    Program files: per-user application location.
    Data/config: %LocalAppData%\Curator.
    Background mode: a current-user scheduled task.

Linux current-user Server
    Program files: ~/.local/lib/curator (portable package convention).
    Data/config: ~/.local/share/Curator on typical desktops.
    Background mode: `systemctl --user enable --now curator-server-user`.

All users requires elevation.

Windows all-users Server
    Program files: Program Files.
    Data/config: %ProgramData%\Curator.
    Background mode: CuratorServer Windows service.

Linux all-users Server
    Program files/static assets: /usr/lib/curator.
    Data/config: /var/lib/curator.
    Background mode: `systemctl enable --now curator-server`.

Host and Viewer app binaries can use either scope while their personal
preferences remain per-user. Older current-user config.json files adjacent to
an executable are read as a compatibility fallback; new writes use the scoped
configuration location.

The Windows registration scripts and Linux service templates live under
packaging/. Service uninstall removes only registration; it deliberately
preserves libraries, archives, backups, and P-HAR environments.


FIRST RUN
---------

Host and local Server browser sessions open the OOBE only for an empty,
unconfigured library. It checks gallery-dl, optional ffprobe/ffmpeg, data
directory writability, download defaults, optional NudeNet/P-HAR consent, and
appearance.
OOBE is local-only: a Tailnet viewer cannot use it.

gallery-dl is required for downloading and defaults to `gallery-dl` on PATH.
ffprobe is optional for duration backfill; ffmpeg is optional for functions
that decode/sample media. Executable-path configuration is local-only and
takes effect after restart.


VIEWER AND TAILNET
------------------

1. Start Host or Server on the library-owning device.
2. Install and sign in to Tailscale on that device and the Viewer device.
3. Configure a restrictive Tailnet grant. Tailnet grants remain the remote
   authorization layer; Curator intentionally has no pairing token.
4. In Viewer, add a named host and run its connectivity test.

Viewer accepts an endpoint only when its hostname/IP appears in local
Tailscale peer inventory and DNS resolution matches that peer's Tailnet IP.
It then requests /api/system/info and checks API protocol, edition, version,
instance identity, capabilities, and Tailnet-only status. A protocol mismatch
is shown before the host is saved/used.

Remote Viewer operations include browsing, playback, downloads, sources,
groups, tags, ratings, and ordinary settings. Destructive Local Admin, OOBE,
service management, executable paths, and P-HAR setup remain on the owning
machine.


SYSTEM INFO
-----------

    GET /api/system/info

Returns edition, package version, API protocol, stable instance identity,
capabilities, and the Tailnet-only assertion. It intentionally does not expose
filesystem paths. Viewer uses it as its post-connect handshake.


LOCAL ADMIN, BACKUPS, AND RESET
-------------------------------

Local Admin is available only to loopback/in-process Host/Server clients.
Tailnet peers get 403 even if their grant allows ordinary library management.

Admin jobs are serialized and show queued/running/succeeded/failed state. The
available jobs include:

  - create, list, download, validate, and stage restore of backups;
  - clear human rating overrides;
  - reset ratings/classifier evidence and requeue eligible analysis;
  - flatten or delete groups while retaining the promised data;
  - clear tag assignments/source-tag rules or interactive history;
  - rebuild thumbnails/derived caches and reconcile library metadata;
  - stage a factory reset that preserves media, archives, P-HAR, and backups;
  - separately remove a managed P-HAR environment or downloaded archives.

Destructive jobs require the displayed typed confirmation, pause/quiesce
workers, make a WAL-aware online SQLite backup, use transactions where data is
mutable, invalidate in-process caches, and fail with rollback rather than a
partial change. Backup archives contain database/configuration only; downloaded
media is intentionally not copied. Restore/reset changes are staged and apply
on restart, with rollback files retained until every database/settings/config
replacement succeeds.


MEDIA AND STORAGE
-----------------

The Media & Storage Settings tab keeps all storage-saving controls opt-in.
`max_download_file_size_bytes` is unlimited by default. When set, Curator
passes the ceiling to gallery-dl as `--filesize-max`; known oversized remote
items remain visible as unavailable placeholders with a skip reason. They are
not entered into the successful download archive, do not fail the source, and
can download on a later re-sync after the ceiling is raised or removed.

`max_source_storage_bytes` is also unlimited by default and is checked before
a remote source starts. A source already at its quota pauses with used and
allowed values plus actions to increase the limit, remove old media, or permit
one sync. An active remote sync can exceed the quota by up to one permitted
file: Curator stops it after indexing that file. Local-folder imports ignore
both remote file-size and source-quota limits unless the explicit local-import
option is enabled.

The minimum-free-disk reserve pauses new downloads before the disk becomes
dangerously full. Thumbnail limits evict derived cache entries least recently
used and never alter originals. Source retention, automatic cleanup, and
archive-age cleanup are disabled by default; each needs its displayed typed
confirmation. Cleanup protects favorites, human-rated media, group members,
and source covers, leaves annotations/metadata as unavailable placeholders,
and never recompresses originals. Removing gallery-dl archives manually or by
age can make older posts eligible for reconsideration on a future sync.


APPEARANCE AND SCROLLING
------------------------

The shell has one primary scrolling region for each view, a separate sidebar
scroller, and modal-body scrollers. Source trees, results, groups/tags,
ratings/review, downloads/discovery/playlists, Viewer hosts, OOBE, Settings,
Admin jobs, and backups should reach their final item even on short screens.

The layout uses dynamic viewport height, min-height: 0 on bounded flex/grid
children, sticky actions, keyboard focus, touch scrolling, and horizontal
overflow controls. Browser tests cover page assets; release UI tests should
exercise desktop, short desktop, tablet, and phone viewport classes.

Theme choices are System, Curator palettes, GTK System, and mapped Adwaita,
Yaru, Arc, and Breeze light/dark presets. Host/Viewer provide client-local GTK
name, light/dark preference, available accent, and font. Curator maps only
those known family names; it never claims to parse arbitrary GTK CSS. Browser
clients use prefers-color-scheme.


P-HAR
-----

P-HAR is off by default and managed separately from NudeNet. Curator pins the
upstream P-HAR source revision and records artifact metadata plus a status
marker under <data-dir>/phar.

The adapter invokes the upstream multimodal demo rather than treating an
arbitrary file as a TorchScript model. Its exact 17-class mapping permits Fast
evidence only for sexual-action/position classes after two consecutive windows
at the required threshold. `kissing` and `fondling` never qualify; `cumshot`
and `facial-cumshot` remain evidence only and never cause automatic Cum.

P-HAR runs in a managed native CUDA or supported AMD ROCm environment. Auto
selection prefers CUDA and then ROCm; Local Admin can record an explicit
backend override, install/resume, cancel, repair, inspect, self-test, and
remove the managed environment. A backend is never ready until environment
setup and a real inference probe pass.

Checkpoint redistribution rights are deliberately not assumed. Until each
required checkpoint has a verified upstream source, rights status, and SHA-256,
Curator downloads nothing and reports P-HAR failed/unready. The NSIS and OOBE
opt-ins record consent only; Local Admin can show the actionable failure,
cancel, repair, self-test, or remove the managed environment.
Failed P-HAR never disables NudeNet/manual review.


PACKAGING AND RELEASES
----------------------

All packages consume the workspace package version. Windows builds produce
current-user and all-users Host/Viewer NSIS installers alongside MSI packages,
plus separate current-user and all-users Server NSIS installers. The Server
installer has an unchecked P-HAR consent checkbox and registers either a
scheduled task or Windows service. Linux produces an all-users Server .deb and
a current-user portable archive with the user-unit installer. Host and Viewer
Linux jobs also attach portable AppImages beside their `.deb`
packages for non-elevated use.

CI validates format, locked workspace builds/tests, strict Clippy, and browser
tests once; product/platform jobs upload their artifacts first; one aggregate
release job attaches them to avoid parallel release races. Packaging smoke
checks cover service definitions, architecture, resources, and server startup.


USE
---

Only add sources you have the right to access. Curator is a local front-end;
you remain responsible for source-site terms, rate limits, account access, and
Tailnet membership.
